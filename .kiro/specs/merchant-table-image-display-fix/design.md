# Merchant Table Image Display Fix - Bugfix Design

## Overview

The bug occurs when merchant tables with images are rendered on the Players or GM screens. The `convert_table_to_html()` function generates valid HTML with interactive buttons and preloaded images, but this HTML is being escaped during the paragraph processing phase of `markdown_to_html()`. The paragraph processing logic wraps non-HTML-looking lines in `<p>` tags and treats them as text content, causing HTML tags to be displayed as literal text instead of being rendered as markup.

The fix requires modifying the paragraph processing logic to detect and skip HTML blocks that were generated by `convert_table_to_html()`, ensuring they are preserved as raw HTML without escaping or wrapping.

## Glossary

- **Bug_Condition (C)**: The condition that triggers the bug - when table HTML generated by `convert_table_to_html()` is processed by the paragraph wrapping logic in `markdown_to_html()`
- **Property (P)**: The desired behavior - table HTML should be preserved as raw HTML without escaping or paragraph wrapping
- **Preservation**: Existing markdown-to-HTML conversion for headers, lists, bold/italic text, links, and non-table paragraphs must remain unchanged
- **markdown_to_html()**: The function in `bin/web/dungeon_turn_app.py` that converts markdown text to styled HTML
- **convert_table_to_html()**: The function in `bin/web/dungeon_turn_app.py` that converts markdown tables to interactive HTML tables with image controls
- **Paragraph Processing**: The final phase of `markdown_to_html()` that wraps non-HTML lines in `<p>` tags

## Bug Details

### Fault Condition

The bug manifests when `convert_table_to_html()` generates HTML containing interactive elements (buttons, images) and this HTML is subsequently processed by the paragraph wrapping logic in `markdown_to_html()`. The paragraph processing incorrectly identifies multi-line HTML blocks as non-HTML content because it only checks if a line starts with `<` and ends with `>`, which fails for HTML blocks spanning multiple lines.

**Formal Specification:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type string (a line from the HTML being processed)
  OUTPUT: boolean
  
  RETURN input.strip() != ""
         AND input IS_PART_OF convert_table_to_html() output
         AND NOT (input.strip().startsWith('<') AND input.strip().endsWith('>'))
         AND input CONTAINS HTML tags or attributes
END FUNCTION
```

### Examples

- **Example 1**: A line containing `<button onclick="toggleImage('row-abc123')"` is not wrapped in `<p>` tags (starts with `<`), but the next line containing `class="toggle-btn text-blue-400..."` IS wrapped in `<p>` tags because it doesn't start with `<`, causing the HTML to be escaped and displayed as text.

- **Example 2**: A line containing `Show Image` followed by `</button>` gets wrapped in `<p>` tags, breaking the button element and displaying the text literally.

- **Example 3**: An `<img>` tag split across multiple lines has its attribute lines wrapped in `<p>` tags, causing the image element to be malformed and displayed as text.

- **Edge Case**: Single-line HTML elements like `<hr class="my-6 border-gray-600">` are correctly preserved because they start with `<` and end with `>`.

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Markdown headers (# ## ### ####) must continue to be converted to styled HTML headers
- Markdown lists (- item) must continue to be converted to styled HTML lists
- Markdown bold (**text**) and italic (*text*) must continue to be converted to styled HTML
- Markdown links ([text](url)) must continue to be converted to styled HTML links
- Non-HTML text lines must continue to be wrapped in `<p>` tags
- Tables without images must continue to render correctly
- All other markdown-to-HTML conversions must remain unchanged

**Scope:**
All inputs that do NOT involve HTML blocks generated by `convert_table_to_html()` should be completely unaffected by this fix. This includes:
- Regular markdown text that should be wrapped in paragraphs
- Markdown formatting (headers, lists, bold, italic, links)
- Non-table content in merchant files
- UI interactions (merchant selector, map zoom, document loading)

## Hypothesized Root Cause

Based on the bug description and code analysis, the root cause is:

1. **Insufficient HTML Detection**: The paragraph processing logic uses a simplistic check (`line.strip().startswith('<') and line.strip().endswith('>')`) that only works for single-line HTML elements. Multi-line HTML blocks generated by `convert_table_to_html()` fail this check.

2. **Line-by-Line Processing**: The paragraph wrapping processes each line independently without tracking whether it's inside an HTML block, causing individual lines of multi-line HTML elements to be wrapped in `<p>` tags.

3. **No HTML Block Tracking**: There's no mechanism to detect when entering/exiting HTML blocks that span multiple lines, such as the `<div>`, `<table>`, `<button>`, and `<img>` elements generated by `convert_table_to_html()`.

4. **Order of Operations**: The paragraph processing happens AFTER `convert_table_to_html()` has already generated valid HTML, so the HTML is being post-processed incorrectly.

## Correctness Properties

Property 1: Fault Condition - Table HTML Preservation

_For any_ line that is part of an HTML block generated by `convert_table_to_html()`, the fixed `markdown_to_html()` function SHALL preserve the line as raw HTML without wrapping it in `<p>` tags or escaping its content, ensuring that buttons, images, and interactive elements render correctly.

**Validates: Requirements 2.1, 2.2, 2.3, 2.4**

Property 2: Preservation - Non-Table Markdown Processing

_For any_ line that is NOT part of an HTML block generated by `convert_table_to_html()` (regular markdown text, headers, lists, etc.), the fixed `markdown_to_html()` function SHALL produce exactly the same HTML output as the original function, preserving all existing markdown-to-HTML conversion behavior.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 3.8**

## Fix Implementation

### Changes Required

Assuming our root cause analysis is correct:

**File**: `bin/web/dungeon_turn_app.py`

**Function**: `markdown_to_html()`

**Specific Changes**:

1. **Add HTML Block Detection**: Modify the paragraph processing section to track when entering/exiting HTML blocks that span multiple lines.
   - Detect opening tags that indicate the start of an HTML block: `<div`, `<table`, `<button`, `<img`, `<script`, `<ul`, `<ol`, `<h1`, `<h2`, `<h3`, `<h4`, `<hr`
   - Track nesting depth for block-level elements
   - Skip paragraph wrapping for all lines inside HTML blocks

2. **Improve HTML Line Detection**: Enhance the check for HTML lines to handle multi-line HTML elements.
   - Current: `line.strip().startswith('<') and line.strip().endswith('>')`
   - Improved: Track whether inside an HTML block OR line starts with `<` OR line is empty

3. **Preserve Empty Lines in HTML Blocks**: Ensure empty lines within HTML blocks are preserved without paragraph wrapping.
   - Empty lines between HTML elements should not trigger paragraph creation

4. **Alternative Approach - Marker-Based**: Use special markers to protect HTML blocks generated by `convert_table_to_html()`.
   - Wrap table HTML in unique markers before other processing
   - Skip all processing for content between markers
   - Remove markers at the end

5. **Simplest Fix - Reorder Processing**: Move paragraph processing BEFORE table conversion, so tables are converted after paragraphs are already wrapped.
   - This ensures table HTML is never subjected to paragraph processing
   - Requires careful testing to ensure other markdown features still work

## Testing Strategy

### Validation Approach

The testing strategy follows a two-phase approach: first, surface counterexamples that demonstrate the bug on unfixed code, then verify the fix works correctly and preserves existing behavior.

### Exploratory Fault Condition Checking

**Goal**: Surface counterexamples that demonstrate the bug BEFORE implementing the fix. Confirm or refute the root cause analysis. If we refute, we will need to re-hypothesize.

**Test Plan**: Write tests that call `markdown_to_html()` with markdown tables containing images, then inspect the output HTML to verify that HTML tags are being escaped or wrapped in `<p>` tags. Run these tests on the UNFIXED code to observe failures and understand the root cause.

**Test Cases**:
1. **Simple Table with Image**: Markdown table with one row containing an image - verify button and img tags are escaped (will fail on unfixed code)
2. **Multi-Row Table**: Markdown table with multiple rows containing images - verify all image controls are escaped (will fail on unfixed code)
3. **Table with Control Buttons**: Verify the "Expand All Images" and "View All Items (Grid)" buttons are escaped (will fail on unfixed code)
4. **Mixed Content**: Markdown with headers, paragraphs, and a table - verify only table HTML is affected (will fail on unfixed code)

**Expected Counterexamples**:
- HTML tags like `<button`, `<img`, `class="..."` are displayed as literal text in the output
- Possible causes: paragraph wrapping logic treats multi-line HTML as text, insufficient HTML block detection

### Fix Checking

**Goal**: Verify that for all inputs where the bug condition holds, the fixed function produces the expected behavior.

**Pseudocode:**
```
FOR ALL input WHERE isBugCondition(input) DO
  result := markdown_to_html_fixed(input)
  ASSERT result CONTAINS valid HTML elements (not escaped)
  ASSERT result DOES_NOT_CONTAIN '<p>' wrapping HTML tags
  ASSERT result CONTAINS interactive buttons and images
END FOR
```

### Preservation Checking

**Goal**: Verify that for all inputs where the bug condition does NOT hold, the fixed function produces the same result as the original function.

**Pseudocode:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT markdown_to_html_original(input) = markdown_to_html_fixed(input)
END FOR
```

**Testing Approach**: Property-based testing is recommended for preservation checking because:
- It generates many test cases automatically across the input domain
- It catches edge cases that manual unit tests might miss
- It provides strong guarantees that behavior is unchanged for all non-table markdown

**Test Plan**: Observe behavior on UNFIXED code first for regular markdown (headers, lists, paragraphs, links), then write property-based tests capturing that behavior.

**Test Cases**:
1. **Header Preservation**: Observe that markdown headers are converted correctly on unfixed code, then write test to verify this continues after fix
2. **List Preservation**: Observe that markdown lists are converted correctly on unfixed code, then write test to verify this continues after fix
3. **Paragraph Preservation**: Observe that regular text is wrapped in `<p>` tags on unfixed code, then write test to verify this continues after fix
4. **Link Preservation**: Observe that markdown links are converted correctly on unfixed code, then write test to verify this continues after fix

### Unit Tests

- Test `markdown_to_html()` with markdown tables containing images - verify HTML is not escaped
- Test `markdown_to_html()` with regular markdown (no tables) - verify output is unchanged
- Test edge cases: empty tables, tables without images, tables at start/end of document
- Test mixed content: markdown with headers, paragraphs, lists, and tables

### Property-Based Tests

- Generate random markdown tables with varying numbers of rows and columns - verify all table HTML is preserved
- Generate random markdown documents with mixed content - verify table HTML is preserved while other markdown is processed correctly
- Test across many scenarios with different combinations of markdown features

### Integration Tests

- Load a merchant file with tables and images in the web UI - verify images display correctly
- Click "Show Image" buttons - verify images appear and buttons change to "Hide Image"
- Click "Expand All Images" - verify all images in the table are displayed
- Click "View All Items (Grid)" - verify modal displays with all item images
- Test on both Players and GM screens - verify consistent behavior
- Test with different merchants - verify all tables render correctly
